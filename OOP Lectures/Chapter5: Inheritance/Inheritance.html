0. Kiến Thức Nền Tảng: Con Trỏ & Tham Chiếu

Trước khi làm chủ OOP và Đa hình, ta bắt buộc phải hiểu rõ hai công cụ thao tác với bộ nhớ cực kỳ quyền lực của C/C++: Con trỏ (Pointer) và Tham chiếu (Reference).

Con Trỏ (Pointer)

Con trỏ là một biến độc lập có vùng nhớ riêng. Nó không lưu giá trị thông thường (như 5, 10), mà lưu địa chỉ bộ nhớ (RAM) của một biến khác.

  • Khai báo bằng dấu *: int* p;
  • Lấy địa chỉ bằng &: p = &x;
  • Giải tham chiếu (truy cập giá trị) bằng *: *p = 10;
  • Đặc điểm: Có thể mang giá trị nullptr (không trỏ đi đâu cả) và có thể thay đổi mục tiêu trỏ liên tục.
int x = 5;
int* p = &x; // p trỏ vào địa chỉ của x
*p = 10;     // Thay đổi giá trị tại địa chỉ đó thành 10
// Kết quả: x = 10
p = nullptr; // p nghỉ chơi, không trỏ x nữa

Tham Chiếu (Reference)

Tham chiếu KHÔNG phải là một biến mới. Nó là một bí danh (nickname) của một biến đã tồn tại. Mọi thao tác trên tham chiếu chính là thao tác trực tiếp trên biến gốc.

  • Khai báo bằng dấu &: int& ref = x;
  • Sử dụng như biến bình thường: ref = 10;
  • Đặc điểm: BẮT BUỘC phải khởi tạo ngay lúc khai báo. KHÔNG thể mang giá trị null, và KHÔNG THỂ thay đổi đối tượng mà nó tham chiếu tới sau khi đã gán.
int x = 5;
int& ref = x; // ref là tên gọi khác của x
ref = 10;     // Tương đương lệnh: x = 10
// Kết quả: x = 10
// ref = y;   // LỖI: Không thể đổi mục tiêu tham chiếu

Under The Hood: Tham chiếu có thực sự tốn RAM không?

Về mặt ngôn ngữ (C++ Standard), tham chiếu không phải là một object, không có địa chỉ riêng (`&ref` sẽ trả về địa chỉ của biến gốc). Tuy nhiên, khi biên dịch xuống mã máy (Assembly), hầu hết các Trình biên dịch (GCC, Clang) cài đặt Tham chiếu hoàn toàn giống hệt Con trỏ (một con trỏ hằng `int* const`). Compiler tự động thêm dấu `*` ngầm định (auto-dereferencing) để bạn không phải viết `*ref`. Tham chiếu sinh ra để làm cho code an toàn hơn (chống NullPointer) và cú pháp sạch hơn con trỏ.

1. Khái Niệm Thừa Kế & Tính Tái Sử Dụng

Thừa kế (Inheritance) là một trong ba trụ cột của OOP (Đóng gói, Kế thừa, Đa hình). Nó cho phép một lớp mới (Lớp dẫn xuất / Derived Class) thừa hưởng các thuộc tính và phương thức từ một lớp đã có (Lớp cơ sở / Base Class). Mục tiêu tối thượng của Thừa kế là Tái sử dụng mã (Code Reusability).

Phân loại Quan hệ trong Thiết kế OOP (Luật Dr. Guru)

Người học OOP thường lạm dụng Kế thừa. Giáo trình nhấn mạnh việc phân biệt rõ hai loại quan hệ:

Quan hệ IS-A (Là một) Quan hệ HAS-A (Có một / Chứa)
Ví dụ: Xe Tải (Truck) LÀ MỘT Xe Cộ (MotorVehicle). Ví dụ: Xe Cộ (MotorVehicle) CÓ MỘT Động cơ (Engine).
Lớp này là một trường hợp đặc thù, cụ thể hóa của lớp kia. Lớp này là một bộ phận cấu thành nên lớp kia.
Cài đặt C++: Dùng cú pháp Kế thừa class B : public A. Cài đặt C++: Dùng Bao gộp (Composition). Khai báo lớp B làm biến thành viên bên trong lớp A: class A { B obj; };

Ký hiệu UML / Sơ đồ lớp (ORD)

Trong biểu đồ thiết kế, mũi tên Kế thừa LUÔN LUÔN trỏ từ Lớp Con hướng lên Lớp Cha (B -> A). Đọc là "B is a A" hoặc "B trỏ tới bản thể A của nó". Mũi tên Bao gộp (HAS-A) là mũi tên hình quả trám (Diamond).

2. Cú Pháp & Quyền Truy Cập (Access Modifiers)

Cú pháp khai báo

class Lớp_Dẫn_Xuất : [Từ_khóa_quyền_truy_cập] Lớp_Cơ_Sở {
    // Phần mở rộng riêng của lớp con
};
// Ví dụ:
class Truck : public MotorVehicle { ... };

Từ khóa protected (Được bảo vệ)

Đây là từ khóa sinh ra DÀNH RIÊNG cho kế thừa.
- Với thế giới bên ngoài (hàm main, các object khác), protected hoạt động như private (Bị cấm truy cập).
- Nhưng với các Lớp dẫn xuất (Lớp con), protected hoạt động như public (Được phép truy cập trực tiếp). Nó là di sản truyền lại cho gia tộc nhưng giấu kín với người ngoài.

Ma trận Quyền Thừa Kế (Inheritance Modes)

Từ khóa đứng trước tên lớp cha quyết định Giới hạn Tối Đa về quyền hạn của các biến kế thừa khi xuống tới lớp con.

Lớp Cha có Kế thừa public Base Kế thừa protected Base Kế thừa private Base
public Giữ nguyên public Hạ xuống protected Bị giam thành private
protected Giữ nguyên protected Giữ nguyên protected Bị giam thành private
private Vẫn được thừa kế vào RAM, nhưng BỊ ẨN (Inaccessible). Lớp con không thể gọi trực tiếp.

Under The Hood: Mặc định của C++

C++ ưu tiên bảo mật. Nếu bạn viết class Derived : Base {}; (quên từ khóa public). C++ sẽ tự động ép nó thành Kế thừa private. Lúc này Base trở thành "Lớp cơ sở riêng" (Private Base Class) của Derived. Tức là hàm main sẽ không biết Derived có gốc gác từ Base, và toàn bộ hàm public của Base bị khóa kín trong lòng Derived.

(Lưu ý: Nếu dùng struct Derived : Base {};, mặc định sẽ là Kế thừa public).

3. Trật Tự Hàm Dựng & Hàm Hủy (Constructors/Destructors)

Quy tắc Khởi tạo (Xây móng trước, cất nhà sau)

Khi tạo một đối tượng của Lớp Dẫn Xuất (ví dụ: Truck t;), phần lõi của Lớp Cơ Sở (MotorVehicle) phải được xây dựng trước. Trình tự chạy Hàm dựng:

  1. Hàm dựng của Lớp Cơ Sở (Base).
  2. Hàm dựng của Lớp Dẫn Xuất (Derived).

Chuyền Tham Số Bằng Danh Sách Khởi Tạo (Initializer List)

Nếu lớp Base không có Hàm dựng mặc định (không tham số), C++ sẽ không tự biết cách tạo móng. Lớp con bắt buộc phải mớm tham số lên cho lớp cha thông qua Cú pháp Khởi tạo:

class MotorVehicle {
public:
    MotorVehicle(int vin, string make) { ... } // Không có hàm rỗng
};

class Truck : public MotorVehicle {
    int payload;
public:
    // CÚ PHÁP CHUẨN MỰC:
    // Truck lấy 3 tham số. Đẩy 2 tham số (v, m) ngược lên cho MotorVehicle.
    // 1 tham số (p) giữ lại để khởi tạo cho mình.
    Truck(int v, string m, int p) : MotorVehicle(v, m), payload(p) {
        // Thân hàm
    }
};

Quy tắc Phá hủy (Dỡ nhà từ nóc xuống, LIFO)

Hàm hủy hoạt động ngược lại với Hàm dựng. C++ dọn dẹp các phần mở rộng của Lớp con trước, sau đó mới dọn lõi Base. Trình tự:

  1. Hàm hủy của Lớp Dẫn Xuất (~Derived).
  2. Hàm hủy của Lớp Cơ Sở (~Base).

Lưu ý: Không bao giờ được gọi tường minh hàm hủy của lớp cha (như Base::~Base()) bên trong hàm hủy của lớp con. C++ tự động làm việc này ngầm định tại dấu } của hàm hủy con.

Lỗi Chết Người: Thiếu Virtual Destructor

Khi bạn thao tác Đa hình (dùng con trỏ Base trỏ vào object Derived), rồi gọi lệnh delete basePtr;. Nếu Hàm hủy của lớp Base KHÔNG CÓ từ khóa virtual, C++ sẽ chỉ nhìn thấy và chạy hàm hủy của lớp Base. Hàm hủy của lớp Derived BỊ BỎ QUA HOÀN TOÀN. Mọi vùng nhớ động (new) được cấp phát trong Derived sẽ bị Rò rỉ vĩnh viễn (Memory Leak).
Luật bất thành văn C++: Nếu class của bạn dự định cho class khác kế thừa, BẮT BUỘC phải viết virtual ~Base() {}.

4. Ghi Đè (Overriding) & Che Khuất Tên (Name Hiding)

Ghi đè phương thức (Overriding)

Khi lớp dẫn xuất không hài lòng với cài đặt phương thức của cha, nó có thể tạo một phương thức MỚI, có CHỮ KÝ HÀM (Tên + Tham số + Kiểu trả về) y hệt để định nghĩa lại hành vi. Việc này gọi là Ghi đè.

Để tái sử dụng sức lao động, hàm con thường gọi lại hàm cha bằng Toán tử định phạm vi (Scope Resolution Operator ::):

void GVCN::tinhLuong() {
    // Lấy lương cơ bản của GiaoVien, rồi cộng thêm phụ cấp chủ nhiệm
    return GiaoVien::tinhLuong() + 500000;
}

Cơ chế Che khuất tên (Name Hiding / Shadowing)

Trong C++, quá trình tra cứu tên (Name Lookup) dừng lại ngay lập tức khi nó tìm thấy cái tên đó ở phạm vi hẹp nhất (Phạm vi của Lớp Con). C++ KHÔNG tự động Overload (nạp chồng) hàm qua biên giới Cha-Con.

class Base { public: void draw(int color); };
class Derived : public Base { public: void draw(); }; // Hàm không tham số

int main() {
    Derived d;
    d.draw(255); // LỖI BIÊN DỊCH !
}

Dù Base có hàm draw(int), nhưng khi Compiler thấy Derived có hàm tên là draw, nó dừng lại và cố nhét số 255 vào hàm không tham số -> Gây lỗi. Hàm draw(int) của cha đã bị Che khuất hoàn toàn.
Khắc phục: Phải viết lệnh using Base::draw; bên trong lớp Derived.

5. Upcast, Downcast & Hiện tượng Cắt Xén (Slicing)

Đây là trái tim của sự tương tác bộ nhớ trong Kế thừa.

1. Upcast (Ép kiểu lên - Luôn an toàn)

Là quá trình đối xử với thực thể của Lớp Dẫn Xuất như là thực thể của Lớp Cơ Sở. Vì "Mọi xe tải (Truck) đều LÀ một phương tiện (MotorVehicle)".

  • Hoạt động ngầm định (Implicit), không cần toán tử ép kiểu.
  • Ví dụ con trỏ: MotorVehicle* mv = new Truck();
  • Ví dụ tham chiếu: MotorVehicle& mvRef = truckObj;
  • Giới hạn: Dù đang trỏ vào Truck, con trỏ mv bị giới hạn "lăng kính". Nó CHỈ nhìn thấy và gọi được các hàm định nghĩa trong MotorVehicle. (Lệnh mv->Load_Cargo() sẽ báo lỗi biên dịch).

2. Downcast (Ép kiểu xuống - Nguy hiểm)

Suy diễn ngược: "Chưa chắc mọi phương tiện đều là Xe Tải". Bắt một con trỏ Lớp Cơ Sở ép xuống Lớp Dẫn Xuất.

  • KHÔNG hoạt động ngầm định. Trình biên dịch sẽ báo lỗi nếu bạn cố tình gán Truck* t = mv;.
  • Phải ép kiểu tường minh: Truck* t = static_cast<Truck*>(mv);
  • Nguy hiểm: Trình biên dịch tin bạn mù quáng khi dùng static_cast. Nếu mv thực chất đang trỏ vào một chiếc Xe Máy (Motorcycle), ép nó thành Truck và gọi hàm của Truck sẽ làm chương trình truy xuất RAM sai lệch và CRASH (Đổ vỡ).

3. Object Slicing (Hiện tượng cắt xén đối tượng)

Upcast/Downcast ở trên nói về Con trỏ và Tham chiếu (Bản chất chỉ là gán địa chỉ, nên dữ liệu dưới RAM của đối tượng hoàn toàn NGUYÊN VẸN).

Nhưng nếu bạn Upcast bằng Phép gán GIÁ TRỊ (Pass-by-value), thảm họa Slicing sẽ xảy ra:

Truck truckObj;        // Truck có 3 biến: số khung, loại máy, và tải trọng
MotorVehicle mv = truckObj; // Cố gắng copy vùng nhớ Truck vào khuôn MotorVehicle

Cơ chế: Trình biên dịch khởi tạo đối tượng mv mới trên RAM. Không gian của mv chỉ có kích thước đủ chứa 2 biến (số khung, loại máy). Nó sẽ tiến hành copy từng byte phần lõi của truckObj sang. Toàn bộ phần biến mở rộng (tải trọng) của truckObj vì không có chỗ chứa nên bị dùng "dao" gọt sạch (Sliced off) và vứt đi.

-> Khuyến cáo: Luôn sử dụng Con trỏ (*) hoặc Tham chiếu (&) khi truyền đối tượng đa hình để tránh Slicing.

6. Đa Kế Thừa (Multiple Inheritance) & Khử Mơ Hồ

Cú pháp & Lưới Hàm dựng

C++ cho phép một Lớp con có nhiều Lớp cha. Phải chỉ định rõ quyền truy cập cho TỪNG lớp cha phân cách bằng dấu phẩy.

class Menu : public OptionList, public Window {
public:
    // Lớp Menu phải nuôi (truyền tham số) cho cả 2 ông bố
    Menu(int optCount, Rect bounds) : OptionList(optCount), Window(bounds) { ... }
};

Sự Cấp Nghĩa / Mơ hồ (Ambiguity)

Nếu cả OptionList và Window đều có chung 1 hàm tên là Highlight(). Khi gọi menuObj.Highlight(), Compiler sẽ bị đứng hình vì không biết gọi hàm của cha nào.
Cách khử mơ hồ: Phải chỉ đường dẫn tường minh bằng toán tử phạm vi: menuObj.Window::Highlight();.

Vấn đề Kim Cương (Diamond Problem) & Lớp Cơ Sở Ảo

Đây là rắc rối lớn nhất của Đa kế thừa. Nếu OptionList và Window cùng kế thừa từ ông nội Widget. Khi Menu kế thừa cả hai, vô tình Menu chứa trong bụng mình TẬN 2 BẢN SAO của Widget. Dư thừa bộ nhớ và nhập nhằng dữ liệu.

Giải pháp: Virtual Base Class (Kế thừa ảo)

C++ yêu cầu ngay từ lúc OptionList và Window sinh ra, chúng phải khai báo virtual public Widget. Thông điệp này có nghĩa: "Gốc rễ Widget này là của chung. Ai đa kế thừa tôi thì xin hãy gộp bản sao Widget lại làm một".

class Widget { ... };
class OptionList : virtual public Widget { ... };
class Window : virtual public Widget { ... };

class Menu : public OptionList, public Window {
public:
    // NHIỆM VỤ ĐẶC BIỆT: Lớp xa nhất (Menu) phải đích thân gọi Constructor của ông nội
    Menu(...) : Widget(...), OptionList(...), Window(...) {}
};

7. Tiêu Chuẩn Hiện Đại: C++11 Keywords

Chuẩn C++11 mang đến hai từ khóa tuyệt vời giúp OOP trở nên cực kỳ chặt chẽ, chống lại các sai lầm do con người gây ra khi Kế thừa.

override (Cưỡng ép Ghi đè)

Hành động ghi đè đòi hỏi bạn phải viết chữ ký hàm Y HỆT lớp cha. Nếu bạn lỡ gõ sai chính tả (`Drw()` thay vì `Draw()`), hoặc nhầm tham số (`int` thành `double`). C++ cũ sẽ coi đó là hàm mới, không báo lỗi, gây bug logic.
Thêm từ khóa override ở cuối hàm con. Compiler sẽ dò lên hàm cha, nếu không thấy hàm nào y hệt để ghi đè, nó sẽ BÁO LỖI BIÊN DỊCH BẢO VỆ BẠN.

class Base { virtual void draw() {} };
class Derived : public Base {
    void draw() override { ... } // An toàn tuyệt đối
    void draw(int color) override { ... } // Báo lỗi ngay lập tức vì không khớp chữ ký
};

final (Tuyệt tự / Khóa hàm)

Cấm kế thừa tiếp, hoặc cấm ghi đè tiếp.

  • class String final { ... };: Lớp String này bị "khóa", không class nào được phép kế thừa từ nó (Tuyệt tự). Tăng cường bảo mật cấu trúc cốt lõi.
  • virtual void auth() final { ... }: Hàm kiểm tra bảo mật này đã là bản chót, các lớp con bên dưới được quyền dùng, nhưng CẤM ghi đè (để tránh bị hacker viết lại hàm auth ở lớp con).
